EXP 15

Mobile Security — Android Traffic Interception

Android Studio · Burp Suite · ADB · Windows CMD
Aim Intercept HTTP and HTTPS traffic from Android emulator using Burp Suite as a proxy.
1
Open CMD → Navigate to Emulator Folder
# Open Command Prompt on Windows, then:
cd C:\Users\Admin\AppData\Local\Android\Sdk\emulator
2
List Available Virtual Devices
emulator -list-avds
# Output: Pixel_9  (or Pixel_2 etc.)
3
Start Emulator with Burp Proxy
10.0.2.2 is how the Android emulator reaches the Windows host machine.
emulator -avd Pixel_9 -http-proxy http://10.0.2.2:8080
4
Configure Burp Suite to Accept All Interfaces
Do this inside Burp Suite GUI — not terminal.
Proxy → Proxy Settings → Proxy Listeners → Edit
→ Binding tab → Select: All interfaces → OK
→ Intercept ON
5
Set Proxy via ADB (if emulator settings don't save)
# Open a NEW CMD window:
cd C:\Users\Admin\AppData\Local\Android\Sdk\platform-tools

adb devices
# Should show: emulator-5554  device

adb shell settings put global http_proxy 10.0.2.2:8080

# Verify it's set:
adb shell settings get global http_proxy
# Output: 10.0.2.2:8080
6
Test HTTP Interception
In the Android emulator, open Chrome browser.
Visit: http://example.com

→ Go to Burp Suite → Proxy → HTTP History
→ You should see the request appear ✅
7
Export Burp CA Certificate (for HTTPS)
Burp Suite → Proxy → Proxy Settings
→ Import/Export CA Certificate
→ Certificate in DER format
→ Save as: burpcer.der  (in Downloads folder)
8
Push Certificate to Emulator
adb push C:\Users\Admin\Downloads\burpcer.der /sdcard/Download/
9
Install Certificate in Emulator
Settings → Security & Privacy
→ More Security & Privacy
→ Encryption & Credentials
→ Install a Certificate → CA Certificate
→ Select: burpcer.der ✅
10
Verify HTTPS Interception
Visit in emulator Chrome: https://example.com

→ Burp Suite → Proxy → HTTP History
→ HTTPS request now visible ✅
Result

Android application network traffic was successfully intercepted and analysed using Burp Suite by configuring proxy settings in the Android emulator and installing the Burp Suite CA certificate. Both HTTP and HTTPS traffic were captured.

EXP 16

IoT Device Security — Default Passwords & Open Ports

Docker (Windows) · Nmap (Kali Linux) · Browser DevTools
Aim Identify open ports, default credentials, and unencrypted communication on a simulated IoT device.
1
Deploy Simulated IoT Device (Windows)
docker run -d -p 8090:3000 --name juiceshop bkimminich/juice-shop

# Open browser → http://localhost:8090
# This is your simulated IoT device dashboard
2
Find Windows IP Address
Run this in Windows CMD. Note down the IPv4 address.
ipconfig
# Look for: IPv4 Address . . . : 192.168.0.148
# This is the IP Kali will scan
3
Scan from Kali Linux using Nmap
Switch to Kali Linux machine. Replace IP with your actual Windows IP.
nmap -sV 192.168.0.148

# -sV = service version detection
# Expected output:
# PORT     STATE SERVICE VERSION
# 8090/tcp open  http    Node.js (Express)
# 135/tcp  open  msrpc   Microsoft Windows RPC
# 445/tcp  open  microsoft-ds
4
Test Default Credentials (Windows Browser)
Go to http://localhost:8090 → click Account → Login
Email:    admin@juice-sh.op
Password: admin123

# Successful login = Default password vulnerability ✅
5
Check Unencrypted Communication
In browser on Juice Shop page:
Press F12 → Network tab → reload page
→ Check Protocol column: shows "http" not "https"
→ All data transmitted in plain text = vulnerability ✅
Result

The experiment demonstrated how an attacker on the same network can identify open ports (8090), detect running services and versions via Nmap, gain unauthorized access using default credentials (admin@juice-sh.op / admin123), and confirm unencrypted HTTP communication through browser DevTools.

EXP 17

Disk Forensics — dc3dd and Autopsy

Kali Linux · dd · mkfs · Autopsy
Aim Create a forensic disk image and analyze digital evidence using Autopsy.
1
Open Terminal
Ctrl + Alt + T
2
Create Sample Evidence File
This simulates a file left by a user — to be discovered during forensic analysis.
echo "Cybersecurity Lab Evidence" > evidence.txt
ls
# Verify: evidence.txt appears in listing
3
Check Disk Partitions
lsblk
# Output example:
# sda
# ├─sda1   ← this is used for real disk imaging
# └─sda2
4
Create 100MB Virtual Disk Image
if = input (zeros), of = output file, bs = block size, count = number of blocks
dd if=/dev/zero of=practice_disk.dd bs=1M count=100
5
Format the Disk
Gives the disk a filesystem so Autopsy can read it.
mkfs.ext4 practice_disk.dd
6
Verify the Image Was Created
ls -lh practice_disk.dd
# Should show: 100M practice_disk.dd
7
Launch Autopsy
autopsy
# Terminal shows URL → open in browser:
# http://localhost:9999/autopsy
8
Create New Case in Autopsy
Click: Create New Case
→ Case Name: CyberLabCase
→ Description: Kali Linux forensic investigation
→ Investigator: (your name)
→ Click: New Case → OK
9
Add Host
Click: Add Host
→ Host Name: KaliLabMachine
→ All other fields: Leave Blank
→ Click: Add Host → OK
10
Add Disk Image
Click: Add Image → Add Image File
→ Browse to: /home/kali/practice_disk.dd
→ Import Method: Symlink
→ Click: Next
# Autopsy begins analyzing the disk image
11
Analyze Evidence
Click: File Analysis      → view all files on disk
Click: Keyword Search      → search for "evidence"
Click: File Type           → filter by images, docs
Click: Deleted Files       → files deleted but recoverable
Click: Meta Data           → timestamps (created/modified)
Result

A 100MB forensic disk image was successfully created using the dd command and formatted using mkfs.ext4. The image was imported into Autopsy at localhost:9999. File artifacts, metadata, and deleted files were examined. Hashing confirmed the integrity of the acquired image.

EXP 18

Log File Analysis for Incident Detection

Kali Linux · journalctl · grep · awk · ssh
Aim Analyze system log files and detect suspicious activities such as failed login attempts and brute force attacks.
1
Navigate to Log Directory
cd /var/log
ls
# Key files:
# apache2/   → web server logs
# journal/   → system logs (most important)
# wtmp       → successful logins
# btmp       → failed logins
# dpkg.log   → package activity
2
View Successful Logins
last
# Shows: who logged in, when, from where
3
View Failed Logins
sudo lastb
# Shows all failed login attempts
# Repeated entries from same user = suspicious
4
Setup SSH Server
sudo apt install openssh-server -y
sudo service ssh start
sudo service ssh status
# Should show: active (running)
5
Simulate Brute Force Attack
Run this command 5–10 times. Enter a wrong password each time. Press Ctrl+C to cancel between attempts.
ssh fakeuser@localhost
# Type wrong password → press Enter → Ctrl+C → repeat
# Do this 5-10 times to generate log data
6
Detect Failed Login Attempts
journalctl | grep "Failed password"
# Output:
# May 06 11:23:11 kali sshd[1234]: Failed password for fakeuser from 127.0.0.1 port 54321
# May 06 11:23:14 kali sshd[1235]: Failed password for fakeuser from 127.0.0.1 port 54322
7
Extract Suspicious IP Address
journalctl | grep "Failed password" | awk '{print $11}'
# Output:
# 127.0.0.1
# 127.0.0.1
# 127.0.0.1
8
Count Attempts Per IP (Key Finding)
This is the most important command — shows brute force clearly.
journalctl | grep "Failed password" | awk '{print $11}' | sort | uniq -c | sort -nr
# Output:
# 10 127.0.0.1   ← 10 attempts = brute force detected ✅
9
Additional Log Commands
# All system logs:
journalctl | less

# SSH activity only:
journalctl | grep ssh

# System errors:
journalctl | grep -i error

# Real-time live monitoring:
sudo journalctl -f

# Last 10 minutes:
journalctl --since "10 minutes ago"

# Apache 404 errors (scanning attacks):
grep "404" /var/log/apache2/access.log

# Package install activity:
less /var/log/dpkg.log
Result

System log files were analyzed using Linux tools including journalctl, grep, awk, and last. Failed SSH login attempts were simulated and successfully detected. Multiple failed attempts (10 attempts) from IP address 127.0.0.1 were identified, indicating a simulated brute force attack. Real-time monitoring was performed using journalctl -f.

EXP 19

Network Forensics Using Wireshark

Kali Linux · Wireshark · ping · curl
Aim Capture and analyze network packets using Wireshark to understand network forensics techniques.
1
Fix Permissions (Run Once)
Only needed if you see a permissions error when starting Wireshark.
sudo dpkg-reconfigure wireshark-common
# Select YES when asked about non-superusers capturing packets

sudo usermod -a -G wireshark $USER

newgrp wireshark
# Applies group change without full logout
2
Launch Wireshark
wireshark &
# & runs it in background so terminal stays free
3
Select Interface and Start Capture
Double-click: wlp3s0   ← Wi-Fi interface (active one)
# OR: eth0 if on wired connection
# Packets start scrolling immediately
4
Generate Network Traffic
Open a new terminal while Wireshark is capturing.
# Generate ICMP (ping) traffic:
ping google.com -c 5

# Generate HTTP traffic:
curl http://example.com

# Generate DNS traffic:
nslookup google.com
5
Apply Filters (Type in Filter Bar → Press Enter)
# TCP packets only:
tcp

# UDP packets only:
udp

# HTTP traffic only:
http

# Get your IP first:
ip a
# Look for inet under wlp3s0 e.g. 192.168.0.105

# Filter by your IP:
ip.addr == 192.168.0.105

# Filter by source IP:
ip.src == 192.168.0.105

# Filter by port:
tcp.port == 80
6
Analyze a Packet — Expand Layers
Click any packet → middle panel shows these layers. Click ▼ to expand each.
▼ Frame              → capture info, timestamp
▼ Ethernet II        → MAC addresses (src & dst)
▼ Internet Protocol  → IP addresses (src & dst)
▼ TCP                → port numbers, SYN/ACK flags
▼ HTTP               → GET/POST, URL, response code
7
Follow TCP Stream
Shows the full client-server conversation in readable text.
Right-click any HTTP packet
→ Follow → TCP Stream
# Popup shows full conversation:
# GET / HTTP/1.1
# Host: example.com
# ...
# HTTP/1.1 200 OK
8
Protocol Statistics
Menu → Statistics → Protocol Hierarchy
# Shows breakdown: % TCP, % UDP, % HTTP etc.
# Take a screenshot of this for your record
9
Stop Capture and Save
Click: Red Square button  → stops capture

File → Save As → capture.pcap → Save

# Export HTTP objects (files transferred):
File → Export Objects → HTTP
Result

Network packets were successfully captured on the wlp3s0 (Wi-Fi) interface using Wireshark. Filters were applied to isolate TCP, UDP, and HTTP traffic. A specific IP address was filtered using ip.addr. The TCP stream was followed to read the full client-server HTTP conversation. Protocol hierarchy statistics confirmed the distribution of network protocols, demonstrating how Wireshark aids in network forensics and intrusion detection.
